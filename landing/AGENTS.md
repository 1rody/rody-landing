# Next.js Agent Rules

Rules for AI agents and models working on this project.

**IMPORTANT:** This website was not built using AI. Respect the original implementation, inspect existing code before making changes, and follow established conventions. Avoid unnecessary rewrites or changes to the project's identity.

## 1. Code Style & Formatting

### 1.1. Client Components

If a component requires client-side functionality, add `'use client'` at the beginning of the file, before imports.

```tsx
'use client'


1.2. Imports
Separate imports into two sections with a blank line between them.
Basic imports: Next.js, React, and structural libraries or components.
import Link from 'next/link'
import Image from 'next/image'


Other imports: Project-specific components, subsections, utilities, and functions.
import Stripe from '@/src/components/landing/misc/Stripe'
import showInformation from '@/src/utils/card'


1.3. Functions
Use named function declarations for default exports.
export default function FunctionName() {
    return (
        <main>
            ...
        </main>
    )
}


1.4. JSX & Tailwind Formatting
Keep JSX organized, readable, and consistent with the existing codebase.
- Keep attributes on one line whenever practical.
- Preserve the project's preferred inline className formatting.
- Keep Tailwind classes together in the opening tag.
- Preserve the existing utility-class ordering and organization.
- Avoid unnecessary line breaks, wrappers, and formatting changes.
- Do not reorganize class names unless necessary.

Example:
<footer className="flex flex-col overflow-hidden relative z-20 h-fit items-center justify-center w-full" />

<Image alt="RodyLanding Title image background" width={1920} height={1080} src="/assets/backgrounds/rody.svg" />

<div className="relative z-5 flex v w-full items-center overflow-hidden bg-amber-200 p-10 shadow-2xl sticky top-[160px]" />


Preserve the author's class ordering and formatting style, even when it differs from conventional Tailwind ordering. Do not silently correct unusual class values unless the task requires it.

2. Naming Conventions
Follow these naming conventions consistently.
- Folders: kebab-case, e.g. landing-sections/
- Files: kebab-case where applicable, e.g. hero-section.tsx
- Variables: camelCase, e.g. projectList
- Functions: camelCase, e.g. showInformation()
- React components: PascalCase, e.g. HeroSection
- Classes and types: PascalCase, e.g. ProjectCard
- Constants: UPPER_SNAKE_CASE for true global constants, e.g. MAX_PROJECTS
- CSS classes: kebab-case, e.g. hero-title
- Environment variables: UPPER_SNAKE_CASE, e.g. NEXT_PUBLIC_API_URL

2.1. Case Styles
Use the correct casing for each context.
- camelCase: projectList
- PascalCase: ProjectList
- kebab-case: project-list
- snake_case: project_list
- SCREAMING_SNAKE_CASE: PROJECT_LIST
Do not confuse PascalCase with camelCase. React components use PascalCase; ordinary variables and functions use camelCase.
3. Git & Conventional Commits
Use Conventional Commits when creating commit messages.
Format:
type(scope): description
Common types:
- feat: new features
- fix: bug fixes
- refactor: code restructuring without behavior changes
- style: formatting and styling changes without functional changes
- perf: performance improvements
- docs: documentation changes
- test: tests
- chore: maintenance
- build: build system and dependency changes
- ci: CI/CD changes
Examples:
feat(landing): add project showcase section
fix(navigation): resolve mobile menu behavior
refactor(components): simplify hero section
style(landing): adjust responsive spacing
docs: update agent rules


Keep commit messages concise and specific. Do not create commits unless explicitly requested.
4. TypeScript & Next.js
- Prefer TypeScript and TSX over JavaScript and JSX.
- Use Server Components by default and Client Components only when client-side functionality is required.
- Use Next.js APIs such as next/link and next/image where appropriate.
- Follow the existing architecture, aliases, folder structure, and dependency choices.
- Reuse existing components and utilities instead of duplicating functionality.
- Avoid unnecessary dependencies, abstractions, and refactoring.
5. Tailwind CSS
- Use Tailwind CSS utility classes according to the project's existing conventions.
- Preserve class ordering, responsive behavior, spacing, colors, and visual design.
- Avoid redundant utilities and unnecessary custom CSS.
- Do not modify animations, transitions, or responsive behavior unless required.
- Do not replace existing styling patterns with personal preferences.
6. Agent Rules
- Inspect relevant files before modifying them.
- Treat existing code as an intentional, manually developed implementation.
- Do not assume the codebase was generated by AI.
- Preserve existing functionality, visual identity, and coding conventions.
- Make only the changes necessary to fulfill the task.
- Avoid speculative rewrites and unrelated modifications.
- Follow established project patterns instead of imposing new ones
